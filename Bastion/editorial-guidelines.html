Editorial Guidelines

This page is about maintaining the wiki, not about the story. It isn't lore, it has no in-universe voice, and it's deliberately left out of the sidebar so readers don't stumble into it. If you're an AI assistant picking up work on this archive in a new conversation: read this page first, before touching any file.

Why this page exists

Each new chat session starts with no memory of previous ones. The person maintaining this archive has to re-explain conventions from scratch every time, which is slow and error-prone — and on at least one occasion an assistant working on this archive stated something as fact that wasn't actually in the source text. This page is the fix: a single place documenting how this wiki is built, so a new session can orient itself by reading a file instead of being told everything again.

This only works if it's actually read. Uploading or linking the current site to a new session doesn't guarantee this page gets opened before edits start — say so explicitly at the start of the conversation.

Sourcing discipline

This is the rule that exists because of a real mistake, not a hypothetical one: while writing the "Hell" overview article, an assistant stated that Jova Spike ruled LastRock "for over a century." The source text never says this — it only says she died there less than a year before her current rebirth. The duration was invented while writing connective narrative prose, and stated as if it were sourced.

The failure mode: infobox fields and Trivia bullets get built mechanically from specific lines and are comparatively safe. Connective or summary prose — the kind that exists to make an article read smoothly, like region overviews, "why this matters" sections, or one-line character blurbs — is where invented specifics slip in, because it feels like writing rather than transcribing.

The rule going forward: any concrete claim in connective prose (a number, a duration, a cause-and-effect statement, "the first," "the only," etc.) must trace to an actual line in the source text. If it's a reasonable inference rather than a stated fact, say so ("presumably," "it's not stated how long, but…") instead of asserting it plainly. When in doubt, cut the specific rather than guess at one.

Gauntlet deaths aren't deaths

Eliminations during a Gauntlet run are not real deaths — the text is explicit that Gauntlet participants who are "killed" inside a run are ejected/knocked out, not actually killed. Wiki pages must not dramatize these as deaths: no "Dies in Chapter X" Trivia bullets, no such events in a "Last death" infobox field, and if mentioned at all, describe them neutrally ("eliminated from the run," "knocked out").

This rule is included deliberately, not as boilerplate. An earlier assistant working on this archive over-corrected on this exact rule once — over-applying it somewhere it didn't belong — and had to be walked back by the person maintaining the wiki. A rule with a real track record of being misapplied, in either direction, is exactly the kind worth writing down rather than re-deriving from instinct each session.

Flag conflicts, don't silently resolve them

When new source material contradicts something already on the wiki (see: the Amity entry in Defenders of Bastion, where Book 1 says he dies and Book 2 shows him alive), don't quietly pick a side or delete either claim. Add an inline note flagging the discrepancy and explaining what's known, and say so explicitly when reporting back. This project has explicit prior feedback that silently "fixing" continuity by guessing which source is right is worse than leaving a visible flag.

Chapter references must name the book

Book 2 restarts chapter numbering from Chapter 1, so a bare "Chapter 12" is ambiguous. Every chapter reference on the wiki must be prefixed with the book: "Book 1, Chapter 12" or "Book 2, Chapter 12."

The full character page template

Characters with enough material get a full page, in this section order: intro paragraph → a .section-jumps anchor bar → Appearance → Personality → Biography (subdivided by book using the accordion pattern below, once a character has material from more than one book) → Abilities → Relationships (with per-relationship <h3> subsections) → Trivia → a pull-quote (.archive-quote) → an .infobox aside with exactly ten fields (Also known as, Status, Rank, Highest rank attained, Rebirths, Last death, First appears, Affiliation, Allies, Enemies) → a .stub-notice → .category-tags → the standard footer.

Biography accordion

Once a character's Biography spans more than one book, wrap each book's content in <details class="bio-book"><summary>Book N</summary>… </details>. Each book toggles independently — this is not a single-open accordion, and doesn't use JavaScript. The most recent book defaults open (the open attribute); earlier books default closed. Existing anchor links into a character's Biography section (e.g. a link to scorio.html#biography) still resolve — the id lives on the <h2>, outside the accordion — but they'll land on a heading with the linked book's content possibly collapsed. That's an accepted tradeoff, not a bug.

The lean minor-character template

Characters without enough material for the full template still get their own page (rather than living inside a combined list) using a leaner structure: eyebrow → title → one-line subtitle → a two-column layout with a single flexible body (no forced Appearance/Personality/Relationships headers) and a slim .infobox with only three fields (Status, Affiliation, First appears) → a .cut-note explaining it's a minor entry → .category-tags. It can grow into the full template later without moving or renaming the file.

Genuine multi-person ensembles that share one scene or fate (like Defenders of Bastion or The Warrens Group) get one shared lean page with a roster, rather than being split into a page per person.

Sidebar navigation

The Characters group is permanently fixed at Scorio, Lianshi, Leonis, Naomi, and Other Characters — no one else is added here regardless of how central they become; promoted characters get a card in Other Characters instead. Places are grouped into hub clusters with a clickable parent and indented .nav-sub children: Bastion (Academy, Warrens, Old Academy) and Rascor Plains (Fiery Shoals). Systems & Lore is a flat list of primer/reference articles, currently ending with Hell.

Pages the sidebar doesn't need to carry — supplementary geography or history that isn't essential to following the main story — use the "deep cut" pattern instead: an eyebrow reading "Deep Cut · Not linked from the main index," and no entry in any nav-group. They're still reachable via inline links and the search index.

Delivery workflow

There's no push access to the canonical GitHub repo (Vehnum/Bastion). Every change gets packaged as a zip and handed over for manual re-upload. Before shipping: run a link/anchor integrity check across every HTML file (every href/src resolves to a real file, and every #fragment resolves to a real id in the target), remove any scratch files (Python scripts, notes) from the working copy, zip, verify contents with unzip -l, and only then hand it over.

Search index

search-index.js needs a new entry any time a page is added, moved, or renamed — title, type, url, and a handful of keywords someone might actually search for. Check it resolves with node --check search-index.js and that every url in it points to a real file before shipping.
